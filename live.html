01 The vision

The stakeholder's intent, stated crisply.

What we're building

In the chat view there is a "Live" button. Click it and a visualizer appears that reacts to both the user's voice and the agent's voice. The user has a hands-free conversation with EA. At the same time, the conversation is happening in the UI — appearing as messages in the chat — whether or not the chat UI is focused, on the same URL. No phone call. All in-browser. In the correct chat view.

Verified achievable

Every element of this maps directly onto what ElevenLabs Speech Engine provides. Nothing in the vision requires a capability Speech Engine lacks. The hard part is not the voice transport — it's syncing the spoken conversation into the existing chat-message machinery (§05–06) and deciding where the EA brain runs (§07).

One-lane principle

Stakeholder preference: one lane, not two. Voice and text are the same conversation in the same chat thread (chatId), interleaving freely. The chat UI may be passive during voice (it reflects what's said; it doesn't need to drive interactive widgets). This shapes every decision below.

02 What Speech Engine actually is

Dispelling the fog around "sits on top of your existing agent." verified against docs + installed SDK

Speech Engine is not an AI. It is a real-time voice I/O wrapper. It does exactly two things: STT (transcribe the user's speech to text) and TTS (speak text your server sends back). It also manages connection lifecycle, turn-taking, and interruption detection. That's it. The brain is yours.

ElevenLabs' own words (overview/capabilities/speech-engine)

"ElevenLabs Speech Engine adds voice capabilities to any chat agent. ElevenLabs handles speech-to-text and text-to-speech while your server provides the LLM logic. The SDK manages connection lifecycle, turn-taking, and interruption detection so you can focus on your agent's behavior."

So "sits on top of your existing agent" means: it wraps voice around the exact same brain that powers text chat. ElevenLabs never sees your system prompt, your tools, or your Gemini call. The verified data flow:

// per turn, verified from quickstart Mermaid + SpeechEngineSession.d.ts
Browser   ──audio──►   ElevenLabs   ──transcript text──►   YOUR server
                                                              │
                                                       YOUR LLM logic
                                                       (the EA brain)
                                                              │
Browser   ◄──audio──   ElevenLabs   ◄──response text──   session.sendResponse()
You get the text, both sides (verified)

On every turn, onTranscript receives the full conversation history as TranscriptMessage { role: "user" | "agent"; content: string }. So the browser always has the text of what was said and what EA replied — which is precisely what we mirror into the chat UI (§06). sendResponse() accepts a string or a streaming async-iterable, and auto-extracts text from OpenAI / Anthropic / Gemini stream formats (verified in SpeechEngineSession.d.ts L66–75) — so an AI SDK streamText result pipes straight into TTS.

The alternative product — ElevenAgents — is the wrong fit

ElevenLabs also sells "ElevenAgents," a fully hosted solution where they provide the LLM, knowledge base, and tools. That would mean a second agent living at ElevenLabs, divorced from our EA brain, prompts, memory, and crisis guardrails. We are deliberately not using ElevenAgents. Speech Engine (bring-your-own-LLM) is the correct choice precisely because it keeps the brain ours.

03 Why the AI SDK alone can't do this

Ruling out the "experimental speech feature" path. verified against AI SDK v6 docs

A natural question: the AI SDK has speech features and supports ElevenLabs — can't we just use those? No — they're one-shot, not real-time.

AI SDK functionWhat it doesReal-time?
experimental_generateSpeech Complete text string → finished audio blob (result.audio.uint8Array) No — one request, one file
experimental_transcribe Complete audio file (readFile('audio.mp3')) → finished text No — reads a file
No realtime primitive exists in the AI SDK

Checked the full v6 Core + UI surface: there is no useVoice/useRealtime hook, no speech-to-speech, no continuous conversation API. Both speech functions are flagged "experimental" and are discrete request/response. ElevenLabs appears only as a model provider for those one-shot calls (eleven_flash_v2_5, scribe_v1), not a realtime layer. Building real-time voice from these primitives would mean hand-rolling mic capture, voice-activity detection, chunking, turn-taking, barge-in, an audio playback queue, and latency management — months of work, and exactly the "cold-start / latency unacceptable" territory we've ruled out.

They're complementary, not competing

Speech Engine = the real-time voice transport (the thing the AI SDK can't do). The AI SDK = the brain (streamText with Gemini + system prompt + tools) — the thing Speech Engine doesn't have. They sit at different layers and we use both.

04 One brain, two surfaces — and the fear of two agents

The stakeholder's central worry: "is there somehow being two agents, one in the app and one on Fly?"

The real risk, named

Today the EA agent is not a reusable thing — it's assembled inline inside /api/chat/route.ts (L335): the system-prompt chain (safetyGuardrails + crisisContext + emotionalAlgebra + … + allStepsGranularDraft), the Gemini model, and the 15+ tool map are all hardcoded in the route handler. There is no exportable "EA agent" object. So if we naively copy that into voice-server/src/responders.ts, we'd create a second agent that drifts: someone edits a prompt file, text changes, voice doesn't. That is the trap to avoid.

The fix: extract the brain into one shared module

Pull the brain out of the route into something like src/lib/ai/ea-agent.ts that owns the prompt assembly, the model, the tool map, and the streamText config. Then both callers use the same module. The route becomes a thin HTTP wrapper; the voice responder becomes a thin transport adapter. One brain. One source of truth. No drift.

                   ┌──────────────────────────┐
                   │  src/lib/ai/ea-agent.ts  │   ← the ONE agent
                   │ (prompt + model + tools) │
                   └────────────┬─────────────┘
                ┌───────────────┴────────────────┐
                ▼                                ▼
   /api/chat/route.ts (Next)          voice responder (Fly)
   text typing → streams to UI        voice transcript → streams to TTS
The catch the Fly/Vercel split imposes

"Both import the same module" has a logistics cost: Fly can't import from the Next app — separate deployments, separate node_modules, separate processes. So sharing the brain is itself a decision (§07.1): either Fly calls back into a Vercel endpoint that runs the real brain (one definitive brain on Vercel; an extra network hop), or the brain is extracted into a shared package both deployments build (no hop, but Fly then needs Supabase creds + all tool code + RLS). This is the pivotal fork.

responders.ts lives on Fly — settled

To answer the literal question: voice-server/src/responders.ts runs on the Fly server (the Node process ElevenLabs dials into over WebSocket). It is not in the Next app. Whether it contains brain logic or merely relays to the brain is the §07.1 decision.

06 The sync mechanism — how voice lands in the chat view

The unlock that makes the one-lane vision tractable. verified against use-ai-chat.ts

The seam: useChat exposes setMessages

The chat UI renders whatever is in the useChat message array — and our hook already destructures setMessages (and addToolOutput) from it (src/hooks/use-ai-chat.ts L59). The array isn't only fed by streaming from /api/chat; we can write to it from any source. Voice is just another source. So voice does not need to route through /api/chat to appear in the chat — it needs to mirror its transcript into the useChat store as it happens.

A turn, step by step

  1. User speaks. ElevenLabs transcribes → the browser client SDK fires a user-transcript event → we append a user message via setMessages. The user's words appear in the chat instantly.
  2. Simultaneously, ElevenLabs forwards that transcript to the Fly responder → it calls the EA brain → streams text back → ElevenLabs speaks it.
  3. As EA's response streams, the browser client SDK fires agent-transcript events → we append/update an assistant message via setMessages. EA's spoken words appear as text, live, in sync with the audio.
Why this satisfies the vision

Both typed and spoken turns ultimately call setMessages on the same store for the same chatId. So the same chat view shows the conversation whether the user spoke or typed — on the same URL, updating live, focused or not. That is the one-lane experience, mechanically.

But the store is ephemeral — three gaps open up

Because voice bypasses /api/chat, the things that route does for free on a text turn do not happen on a voice turn: (1) persistence to Supabase, (2) session-context / memory tools keyed to the conversation, (3) display-tool rendering & the usage / survey-gate signals. Voice messages live only in the client array until we deliberately handle each. These three gaps are the §07 decisions.

06b Voice can't start a conversation — and that's a feature

A single constraint that removes a huge swath of complexity. agreed verified against chat-creation-flow.md

The constraint

Voice is only available inside an already-created chat. The Live button does not appear on the empty /chat new-chat view — it appears once you're in /chat/{id} with a real conversation. You cannot begin a conversation by talking.

Why this is correct, not limiting: chat creation has hard requirements that a voice transcript event simply does not carry. Verified from docs/overview/chat-creation-flow.md:

  • The client generates chatId (crypto.randomUUID()) before the first send — there's no chat to speak into yet.
  • The pre-survey rides the first /api/chat request body — it's captured at chat-creation time, client-side React state until then.
  • The title is generated from the first user message via generateTitleForChat.
  • data-new-chat-created drives the URL update (replaceState → /chat/{id}).
What the constraint buys us

(1) Pre-survey is already satisfied — you can't reach /chat/{id} without having sent a first message that carried the pre-survey, so voice never has to handle pre-survey capture. (2) chatId already exists — voice persistence (§07.2) just appends to a known chat: no creation race, no title generation, no data-new-chat-created. (3) §07.2 shrinks from "voice must replicate chat-creation" to the far narrower "given a known chatId, append turns to messages."

The two side-effects most likely to bite if forgotten

#11 buildCrisisContext silently shapes the system prompt with the user's crisis history every turn. Drop it and EA loses crisis awareness specifically in voice — the worst possible place to lose it, since voice users may be the most vulnerable. This is the #1 thing to not miss.

#21 + completeSession's owing-marker. Completion can fire mid-voice-turn: EA decides the arc is done → calls completeSession → sets postSurveyOwed. In voice this must end the voice session and trigger the survey voice-gate (§08), or the user keeps talking past a completed session and bypasses the mandatory survey.

The reassuring conclusion

Because the brain runs on Vercel, #11–17, #19, #21 all execute in the same shared code the text route uses. The only genuinely voice-specific work is history shaping (#13), persistence (#22–23), and the voice-gate teardown signals (#3, #4, #14, #21). That's a bounded, knowable list — not a fog. The unknowns are now known.

07 The decisions (7.1 settled · 7.2 open · 7.3 settled)

7.1 and 7.3 are now decided; 7.2 remains, with a narrower framing thanks to §06b. 2 settled 1 open

07.1 · Where the EA brain runs for a voice turn settled · Vercel

Decision

Brain on Vercel; Fly relays. Fly's responders.ts does fetch() to a new Vercel route (e.g. /api/voice-turn) running the same shared EA brain as /api/chat; Fly streams the returned text into ElevenLabs TTS. One brain, definitively — memory tools, crisis context, persistence, and RLS all "just work" on Vercel, in the same code the text route uses. Best fit for the "minimize segmentation" preference; the WebRTC token endpoint already lives on Vercel, so the whole server side is consistent. The only cost is one Fly→Vercel hop per turn (tens of ms — negligible for therapy-paced conversation). No reason was found to run the brain on Fly.

Rejected alternative: brain on Fly via a shared package — no per-turn hop, but Fly would need Supabase creds + RLS + all tool code, adding segmentation, surface area, and drift risk. Not worth the latency saving.

07.2 · How voice turns persist to the DB open

Narrowed framing (thanks to §06b + 7.1)

This is no longer "voice must replicate chat-creation." Because voice only runs inside an existing chatId (§06b) and the brain already runs server-side on Vercel (7.1), the question shrinks to: given a known chat, where does the write happen? The relay endpoint /api/voice-turn is already on the server with DB + RLS access — which reopens the calculus below.

Lean (revised)

Relay persists, server-side

  • Since /api/voice-turn already runs the brain on Vercel with DB access, it can call the same persistFinishedMessages path the text route uses — user turn in, assistant turn out.
  • Reuses the existing, battle-tested persistence (update-or-insert, 3-retry, token stamping) with zero new client round-trip.
  • Open sub-question: the client also needs these messages in its useChat array (via setMessages from transcript events) — so reconcile IDs so the server write and the client mirror don't duplicate.
Alt

Client → tRPC per turn

  • Browser calls a new saveVoiceMessages tRPC after each turn (reuses saveMessages + withRLS).
  • Durable per-turn; but duplicates persistence logic the relay could just do itself.
Alt

Flush on session end

  • Persist nothing mid-call; write the whole transcript when the live session ends.
  • Simplest — but a dropped connection mid-session loses everything.
The crux still to resolve

Who is the source of truth for the message IDs — the client (which mirrors transcript events into useChat via setMessages) or the server relay (which persists)? Whichever generates the ID, the other must use the same one so a page-refresh reload from DB doesn't duplicate what's already on screen. This is the one knot left in 7.2. Tracked in §09 (Risks → "Message ID reconciliation").

07.3 · Display tools / blocks during voice settled · voice-gate

Decision — generalized into one primitive

Rather than suppress display tools or render them passively, we deterministically close the voice connection whenever the UI needs the user's attention, and disable the Live button until the condition clears. EA says something like "take a look at the chat, I need your input," the user interacts in the UI normally (exactly as in text mode), then re-enables voice. This unifies four separate problems into one mechanism — the voice-gate. See §08 for the full design. Crucially, this means display tools, crisis lockout, the survey block, and credit exhaustion do not need bespoke voice handling — they all funnel through the same teardown-and-relock primitive.

08 The voice-gate primitive

One mechanism that resolves four problems: voice and "the user must act in the UI" are mutually exclusive states. agreed direction

The reframe

The hard question "how does voice coexist with UI elements that need input, crisis lockouts, survey blocks, and credit limits?" dissolves once you accept they're mutually exclusive with an active voice session. When any voice-incompatible condition becomes true, voice ends deterministically, EA verbally hands off to the UI, and the Live button stays disabled until the condition clears.

The four triggers, one primitive

TriggerToday (text mode)Voice behavior (via the gate)
Display tool needs inputwidget renders; input bar waitsclose voice → "look at the chat, I need your input" → relock Live until submitted
Crisis lockoutCrisisLockoutModal blocksclose voice → relock Live until lockout clears
Post-survey owedglobal block + survey appendedclose voice → relock Live until survey submitted
Credits exhaustedforbidden:chat rejectionclose voice → relock Live until credits return
Definition

The voice-gate = a set of conditions that, when any is true, voice cannot be active. The brain (on Vercel, where it already evaluates every one of these — see the §06c lifecycle) returns a teardown signal alongside or instead of a response, e.g. { endVoice: true, reason: 'needs_input' | 'crisis' | 'survey' | 'credits' }. The client tears down the ElevenLabs connection and disables Live; the reason drives what EA says on the way out and what UI the user lands in.

// shape of the teardown signal (illustrative, not final)
type VoiceTurnResult =
  | { kind: 'speak'; text: AsyncIterable<string> }       // normal turn → TTS
  | { kind: 'handoff'; reason:                            // gate engaged → end voice
        'needs_input' | 'crisis' | 'survey' | 'credits';
      spokenText?: string }  // optional last words before teardown
Why this is the right shape, not a hack

(1) It dissolves the §07.3 display-tool dilemma — the brain emits display tools exactly as today; the voice layer just detects "this turn needs UI input" and hands off. Voice and the existing text machinery don't fight — they hand off. (2) Pre-stream gates double as voice-gates for free — credits (#3) and survey (#4) are already checked before the model runs (§06c), so the relay can refuse to start a voice turn and return a handoff immediately. (3) Completion mid-turn is handled — when completeSession sets postSurveyOwed (lifecycle #21), the turn resolves to a survey handoff, closing voice and routing the user to the mandatory survey rather than letting them talk past a finished session.

Sub-questions to flesh out later

How EA's "I need your input" line is produced (model-generated vs. a canned voice-mode utterance) · whether teardown is graceful (let the current sentence finish) or immediate · the exact Live-button disabled-state UX and how it re-enables (poll vs. event) · whether needs_input should name which tool so the UI can scroll/focus it.

09 What's already built

The transport layer exists and is validated. deployed

  • voice-server/ — a standalone Node/TS service hosting the Speech Engine WebSocket. Deployed to Fly.io (ea-voice-server.fly.dev, region iad, always-warm config so cold-start never bites). Validated end-to-end: live browser voice conversation routed through it, excellent latency.
  • src/responders.ts — currently placeholder brains (echo, canned) that prove the transport with zero-dependency output. This is where the §07.1 decision lands — either the real EA brain or a relay to Vercel.
  • Responsibility split (settled): the Speech Engine WS host runs on Fly; the WebRTC token endpoint runs on Vercel (stateless, auth-gated, rate-limited). The browser talks only to Vercel (token) + ElevenLabs (audio) — never to Fly directly.
Verified SDK facts (installed @elevenlabs/elevenlabs-js@2.49.1)

engine.attach(engineId, httpServer, "/ws", callbacks) hosts the WS · onTranscript(transcript, signal, session) delivers full history + an abort signal that fires on interruption · session.sendResponse(string | AsyncIterable) streams to TTS and auto-extracts Gemini stream text · new transcript auto-aborts the previous in-flight call (barge-in handled for us).

10 Risks & edges to track

Not blockers — things to keep honest about as we design.

Crisis guardrails — resolved by 7.1

The text brain runs buildCrisisContext() (lifecycle #11) and a flagCrisisDetected tool. With 7.1 = brain on Vercel, these come along for free in the shared brain. Still a must-verify, not a must-design: the §06c inventory flags #11 as the single side-effect most likely to be silently dropped — the implementation must prove crisis context is present on a voice turn. Safety is non-negotiable; voice users may be the most vulnerable. A detected crisis also engages the voice-gate (reason: 'crisis', §08).

Usage / billing on voice turns — deliberately tabled

Text turns deduct 1 message credit in /api/chat's onFinish. Decision: table this for now — there's no clear model yet for what a "voice turn" costs (a turn? a minute? STT/TTS seconds?), and forcing one prematurely would distort the design. The credit-exhaustion gate (refusing to start voice when credits are already zero) is separate and is handled — it's a voice-gate trigger (§08). What's tabled is metering consumption during a voice session. Revisit once we have a metering model; until then voice consumes nothing.

Post-survey gate × voice — resolved by the voice-gate

Issue #27's global block (forbidden:pending_survey) lives in /api/chat. The brain-on-Vercel relay re-applies the same pre-turn checks (checkMessageLimit + owed-survey), so voice can't be an escape hatch around the block. When owed, the relay returns a survey handoff (§08) rather than starting a turn. Also covers completion mid-session (lifecycle #21): completeSession sets postSurveyOwed → next turn resolves to a survey handoff → voice closes, user is routed to the mandatory survey.

Message ID reconciliation — the live knot in 7.2

Two writers exist: the client mirrors transcript events into useChat via setMessages, and the server relay persists the turn (§07.2 lean). They must agree on message IDs or a page-refresh reload from DB will duplicate what's already on screen. Resolve who owns the ID: either the client generates crypto.randomUUID() and passes it to the relay to persist, or the relay returns its IDs for the client to adopt. Mirrors the existing client-ID-generation pattern that prevents chat-creation races. This is the remaining open piece of 7.2.

Interruption / barge-in — already handled

Speech Engine auto-aborts the in-flight response when the user starts speaking (verified). Our brain call just needs to honor the supplied AbortSignal (the AI SDK streamText accepts one). No bespoke turn-taking engine to build.

11 Implementation checklist (provisional)

Reflects settled 7.1 + 7.3. One open item (7.2 ID ownership) gates the persistence steps.

  1. Resolve the 7.2 knot — decide who owns voice message IDs (client vs. relay) so mirror + persistence don't duplicate (§10 risk). Everything in 7.2 follows from this.
  2. Extract the brain from /api/chat/route.ts into src/lib/ai/ea-agent.ts (prompt assembly + model + tools + streamText config), so text and voice share one definition. Refactor the route to consume it (no behavior change to text chat).
  3. Add /api/voice-turn (Vercel) — auth-gated, runs the shared brain, re-applies the pre-stream gates (checkMessageLimit + owed-survey + ownership), and returns either a text stream (speak) or a handoff with a reason (§08). Persists the turn server-side via the existing persistFinishedMessages path (§07.2 lean).
  4. Carry buildCrisisContext through — explicitly verify the voice path includes crisis context (§06c #11) and that a detected crisis returns a crisis handoff.
  5. Point responders.ts (Fly) at /api/voice-turn as a new mode — relay transcript in; on speak stream text to sendResponse honoring the abort signal; on handoff speak the optional last words and signal the client to tear down.
  6. Token route — authenticated Next.js endpoint minting the ElevenLabs WebRTC token (browser-facing, rate-limited).
  7. Live button + visualizer in the chat view — ElevenLabs client SDK; visualizer driven by both audio streams. Button only present inside an existing /chat/{id} (§06b).
  8. UI mirror — wire the client SDK's transcript events into setMessages (user + agent), using the agreed ID-ownership rule (step 1).
  9. The voice-gate — client teardown + Live-button disable keyed on handoff.reason; re-enable when the condition clears (display submitted / lockout over / survey done / credits restored).
  10. Verify — crisis path holds in voice; survey gate not bypassable (incl. mid-session completion); refresh mid-session restores from DB without duplicates.
Tabled / out of scope for v1

Voice usage metering/billing is deliberately tabled (§10) — no consumption model yet; voice consumes no credits for now (the credit-exhaustion gate still applies). Coordinated voice + interactive display widgets (the "full parity" north star) is deferred — in v1 a display tool simply hands off to the UI via the voice-gate. v1 is hands-free conversation mirrored into the chat view, one brain, one thread, durable history, with clean handoffs whenever the UI needs the user.

Summary

Speech Engine is a voice I/O wrapper, not an agent — it does STT + TTS + turn-taking and hands our server the transcript text both ways, so the EA brain stays ours. The vision (Live button, visualizer, hands-free talk appearing live in the same chat thread) is achievable because useChat exposes setMessages: voice is just another source feeding the same message store.
